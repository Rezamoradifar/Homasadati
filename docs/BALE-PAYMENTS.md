# راه‌اندازی پرداخت بله برای هما نت

این اتصال برای ربات [Homanets_bot](https://ble.ir/Homanets_bot) و برنامهٔ Next.js هما نت است. مشتری از سبد خرید وارد گفت‌وگوی ربات می‌شود و صورتحساب را در بله پرداخت می‌کند. رویدادهای ربات با webhook به همان برنامهٔ وب می‌رسند؛ مینی‌اپ یا سرویس جداگانهٔ polling لازم نیست.

طبق [مستندات رسمی بله، بخش پرداخت و کیف‌پول](https://docs.bale.ai/)، پرداخت مشتری به کیف‌پول توسعه‌دهندهٔ ربات در بله می‌رسد. این اتصال به‌خودی‌خود تضمین واریز مستقیم یا زمان تسویه به حساب بانکی شرکت نیست. مالک باید حساب دریافت‌کننده، امکان برداشت، محدودیت‌ها و کارمزدهای مربوط به کیف‌پول خود را با بله تأیید کند.

## پیش‌نیازها

- دسترسی مالک به `@Homanets_bot` در بله و به [BotFather](https://ble.ir/botfather).
- **توکن ربات** برای Bot API و **توکن مستقل کیف‌پول (`provider_token`)** متعلق به همان ربات. این دو مقدار یکسان نیستند؛ نام عمومی ربات جای هیچ‌کدام را نمی‌گیرد.
- دامنهٔ HTTPS معتبر `homanets.com` که از اینترنت و سرورهای بله قابل دسترسی باشد.
- نصب و build موفق نسخهٔ حاوی این اتصال روی سرور، با همان دیتابیس و کلید رمزگذاری قبلی.
- تصمیم روشن دربارهٔ برنامه‌ای که اکنون رویدادهای این ربات را دریافت می‌کند. یک webhook متعلق به اتصال دیگر باید قبل از انتقال بررسی شود.

دستورهای زیر برای نصب `/opt/homay/app` با کاربر `homay` و سرویس‌های `homay` و `homay-worker` هستند. آنها را **پس از نصب نسخهٔ جدید** اجرا کنید. در ارتقای کد، commit و mergeهای اختصاصی سرور را حفظ و با نسخهٔ انتشار تطبیق دهید؛ تاریخچهٔ سرور را با checkout اجباری یا `reset --hard` جایگزین نکنید. مراحل پشتیبان و نگهداری در [راهنمای عملیات](OPERATIONS.md) آمده‌اند؛ شاخه و commit انتشار باید با نسخهٔ واقعی این تغییر تطبیق داشته باشند.

## ۱. تنظیم خصوصی سرور

مقادیر را در منبع فعلی تنظیمات برنامه وارد کنید. اگر وب و worker از `.env.local` می‌خوانند، فایل موجود را با ویرایشگر خصوصی باز کنید:

```bash
sudoedit -u homay /opt/homay/app/.env.local
```

این کلیدها را اضافه یا ویرایش کنید؛ هر کلید فقط یک بار وجود داشته باشد:

```dotenv
APP_ORIGIN=https://homanets.com
BALEPAY_ENABLED=0
BALEPAY_BOT_USERNAME=Homanets_bot
BALEPAY_BOT_TOKEN=
BALEPAY_PROVIDER_TOKEN=
BALEPAY_WEBHOOK_SECRET=
```

توکن‌ها را داخل همان ویرایشگر وارد کنید. آنها را در گفتگو، GitHub، متن دستور، `export TOKEN=...` یا آرگومان `curl` قرار ندهید. هیچ مقدار بله‌ای با پیشوند `NEXT_PUBLIC_` تعریف نشود. `DATABASE_PATH` و **`PLATFORM_MASTER_KEY` موجود را حفظ کنید**؛ برای این اتصال اجرای دوبارهٔ راه‌اندازی اولیه یا ساخت کلید رمزگذاری جدید لازم نیست.

`BALEPAY_WEBHOOK_SECRET` باید تصادفی و دقیقاً ۶۴ نویسهٔ hex باشد. برای ساخت آن بدون چاپ در ترمینال می‌توانید یک فایل موقت خصوصی بسازید:

```bash
cd /opt/homay/app
sudo install -d -m 700 -o homay -g homay /opt/homay/bale-setup-private
sudo -u homay node -e 'require("node:fs").writeFileSync("/opt/homay/bale-setup-private/webhook-secret.private", require("node:crypto").randomBytes(32).toString("hex") + "\n", { mode: 0o600, flag: "wx" })'
sudoedit -u homay /opt/homay/bale-setup-private/webhook-secret.private /opt/homay/app/.env.local
```

در ویرایشگر، مقدار فایل موقت را در `BALEPAY_WEBHOOK_SECRET` قرار دهید. پس از ذخیرهٔ مطمئن تنظیمات، فایل موقت را حذف کنید و `.env.local` را خصوصی نگه دارید:

```bash
sudo -u homay rm -- /opt/homay/bale-setup-private/webhook-secret.private
sudo chmod 600 /opt/homay/app/.env.local
```

فرمان تولید فایل موجود را بازنویسی نمی‌کند. اگر قبلاً secret معتبر دارید، همان را نگه دارید؛ تغییر آن نیازمند هماهنگی انتقال webhook است.

اگر systemd از `EnvironmentFile` جدا استفاده می‌کند، همان منبع معتبر را ویرایش کنید و اطمینان یابید ابزار راه‌اندازی نیز همان تنظیمات را دریافت می‌کند. کپی دوم و متناقض از تنظیمات نسازید. `sudo -u homay npm ...` به‌تنهایی متغیرهای خصوصی سرویس systemd را به ارث نمی‌برد؛ فرمان‌های این راهنما فرض می‌کنند تنظیمات از `.env.local` موجود خوانده می‌شوند. فایل محیط را برای اجرای آن به‌عنوان کد shell، `source` نکنید.

## ۲. آماده‌کردن مسیر webhook و لاگ‌ها

نشانی webhook به‌صورت خودکار از `APP_ORIGIN` و secret ساخته می‌شود. مسیر داخلی آن:

```text
/api/platform/payment/bale/webhook/<secret>
```

secret بخشی از احراز هویت درخواست است. **نشانی کامل webhook را در مستندات عمومی، اسکرین‌شات یا لاگ مشترک ثبت نکنید.** این مسیر باید از HTTPS به همان برنامهٔ Next.js برسد و با صفحهٔ ورود، challenge مرورگر یا cache مسدود نشود.

توکن ربات در مسیر URL درخواست‌های خروجی Bot API قرار می‌گیرد و `provider_token` در بدنهٔ درخواست صورتحساب است. ثبت این URL و بدنه در ابزارهای APM، tracing یا گزارش خطای خروجی نیز باید حذف یا ماسک شود.

پیش از ثبت webhook، ثبت URL کامل این مسیر را در Nginx، CDN و APM حذف یا ماسک کنید. در Nginx می‌توان ثبت access log را برای location این مسیر با `access_log off` متوقف کرد؛ تنظیمات proxy و سرآیندهای همان برنامه باید حفظ شوند. لاگ خطا ممکن است همچنان URI درخواست را داشته باشد؛ دسترسی آن خصوصی بماند و خروجی خام آن به سامانه‌های مشترک فرستاده نشود. برای تنظیم دقیق ثبت لاگ، [مستندات رسمی Nginx](https://nginx.org/en/docs/http/ngx_http_log_module.html) را ببینید. تغییر Nginx باید پیش از reload با `nginx -t` تأیید شود.

## ۳. بررسی بدون تغییر

در این مرحله `BALEPAY_ENABLED=0` بماند. نسخهٔ جدید وب باید با همین تنظیمات اجرا شود تا مسیر webhook در دسترس باشد.

```bash
cd /opt/homay/app
sudo -u homay env NODE_ENV=production npm run platform:bale-setup -- --check
```

این فرمان فقط `getMe` و `getWebhookInfo` را از بله می‌خواند؛ دیتابیس را باز نمی‌کند، webhook را تغییر نمی‌دهد و پیام یا پرداختی ایجاد نمی‌کند. نام ربات برگشتی باید بدون حساسیت به بزرگی حروف، دقیقاً با `Homanets_bot` منطبق باشد.

خروجی شامل نام عمومی ربات و مقادیر boolean است. توکن، URL محرمانه و پاسخ خام ارائه‌دهنده چاپ نمی‌شوند. `webhookMatches: true` یعنی webhook فعلی با تنظیمات این نسخه منطبق است. اگر webhook خالی یا متفاوت باشد، خروجی `webhookMatches: false` و exit code برابر ۱ خواهد بود؛ در حالت خالی هنوز مرحلهٔ ثبت لازم است.

`enabledSetting` فقط مقدار `BALEPAY_ENABLED` را گزارش می‌کند. آمادگی پرداخت علاوه بر آن به رکورد ثبت منطبق در دیتابیس و موفقیت بررسی عملی اتصال نیاز دارد. چون `--check` دیتابیس را نمی‌خواند، خروجی آن آمادگی کامل پرداخت را تأیید نمی‌کند.

اگر ربات webhook متفاوتی دارد، ابتدا مالک اتصال قبلی باید انتقال آن را بررسی کند. خالی بودن webhook نیز به‌تنهایی ثابت نمی‌کند polling دیگری وجود ندارد؛ اجرای هم‌زمان یک مصرف‌کنندهٔ قدیمی رویدادها را پیش از انتقال بررسی کنید. طبق [مستندات بله](https://docs.bale.ai/)، webhook و `getUpdates` دو روش دریافت رویداد هستند.

## ۴. ثبت و تأیید webhook

پس از آماده‌شدن مسیر و بررسی اتصال قبلی:

```bash
cd /opt/homay/app
sudo -u homay env NODE_ENV=production npm run platform:bale-setup -- --register
```

فرمان ابتدا هویت ربات و webhook فعلی را بررسی می‌کند. اگر webhook خالی باشد، نشانی محاسبه‌شده را ثبت می‌کند. اگر همان نشانی قبلاً ثبت شده باشد، آن را دوباره بازنویسی نمی‌کند. وجود هر نشانی متفاوت باعث توقف می‌شود؛ گزینهٔ `--force` وجود ندارد.

پس از مشاهدهٔ مجدد webhook منطبق با `getWebhookInfo`، اثرانگشت تنظیمات جاری در رکورد `registered_config` جدول `p_bale_runtime` ذخیره می‌شود. خروجی موفق باید `botVerified: true`، `webhookMatches: true` و `registrationSaved: true` داشته باشد. `--check` این رکورد را نمی‌سازد؛ حتی برای webhook از قبل منطبق، مرحلهٔ `--register` لازم است.

اگر ثبت بله موفق شد ولی ذخیرهٔ دیتابیس یا تأیید نهایی شکست خورد، پرداخت را فعال نکنید. پس از رفع مشکل، ابتدا `--check` و سپس `--register` را تکرار کنید؛ یک webhook منطبق بازنویسی نمی‌شود. مسیر دیتابیس و مالکیت فایل‌ها باید همان موارد استفاده‌شده توسط وب و worker باشد.

این بررسی، هویت ربات و نشانی webhook را تأیید می‌کند؛ فعال‌بودن کیف‌پول دریافت‌کننده یا یک پرداخت موفق واقعی را اثبات نمی‌کند.

## ۵. فعال‌سازی و بررسی توسط مالک

پس از موفقیت مرحلهٔ ثبت، در همان فایل خصوصی `BALEPAY_ENABLED=1` قرار دهید. نام ربات، توکن‌ها و secret را تغییر ندهید. اثرانگشت ثبت‌شده شامل کلید فعال‌سازی نیست، بنابراین تغییر ۰ به ۱ ثبت را نامعتبر نمی‌کند.

پس از build موفق و نصب نسخهٔ جدید، تنظیمات جدید را به سرویس‌های موجود برسانید:

```bash
sudo systemctl restart homay homay-worker
sudo systemctl is-active homay
sudo systemctl is-active homay-worker
curl --fail --silent --show-error https://homanets.com/api/platform/payment/methods
```

پاسخ روش‌های پرداخت باید `bale: true` داشته باشد. توکن‌های `WALLET-TEST-*` به سفارش‌های عادی متصل نمی‌شوند. آزمون sandbox ارائه‌دهنده باید در محیط و دیتابیس جدا باشد؛ موفقیت تست‌های محلی یا بررسی webhook به معنی دریافت پول واقعی نیست.

**پیش از اعلام آمادگی، انتقال از سایت به ربات باید روی دستگاه واقعی بررسی شود.** مالک با مرورگر گوشی و نسخهٔ واقعی بله، از سبد خرید یک تلاش پرداخت با مبلغ کم ایجاد کند و همان لینک تولیدشدهٔ سایت با الگوی `https://ble.ir/Homanets_bot?start=pay_<opaque>` را باز کند. در صورت نمایش دکمهٔ شروع، آن را بزند و تأیید کند که payload همان تلاش به‌شکل `/start pay_<opaque>` به ربات می‌رسد و صورتحساب همان سفارش و مبلغ ایجاد می‌شود. بازشدن صفحهٔ عمومی ربات بدون انتقال payload کافی نیست؛ برای این بررسی، تایپ دستی فرمان را جایگزین بازکردن لینک نکنید. payload واقعی تلاش را در گزارش عمومی یا لاگ مشترک قرار ندهید.

این بررسی باید مسیر واقعی جابه‌جایی از مرورگر به برنامهٔ بله و شروع گفت‌وگو را پوشش دهد. تست‌های mock فقط رفتار کد در برابر پیام ورودی شبیه‌سازی‌شده را می‌سنجند؛ تحویل payload لینک توسط برنامهٔ بله با این تست‌ها اثبات نشده است. اگر این تحویل کامل نشد، فعال‌سازی عمومی را متوقف و مشکل را بررسی کنید.

پس از موفقیت این مرحله، مالک همان خرید کنترل‌شده و از پیش تأییدشده را پرداخت کند و نتیجه را در سایت ببیند. ثبت سفارش و وضعیت نهایی آن باید با تراکنش و موجودی کیف‌پول مقصد تطبیق داده شود. دوباره بازکردن صفحه یا دریافت مجدد رویداد نباید سفارش یا پورسانت دیگری ایجاد کند. این آزمون انتقال واقعی وجه دارد و باید توسط مالک انجام شود.

## جریان تأیید و موارد پشتیبانی

قرارداد صورتحساب `sendInvoice`، تأیید اولیهٔ `answerPreCheckoutQuery`، رسید `SuccessfulPayment` و استعلام `inquireTransaction` در [مستندات رسمی پرداخت بله](https://docs.bale.ai/) آمده است. استعلام، وضعیت تراکنش، شناسهٔ پرداخت‌کننده و مبلغ ریالی را برمی‌گرداند؛ تأیید اولیه به‌تنهایی اثبات پرداخت نیست.

در این پروژه، سرور پیش از اجازهٔ پرداخت، شناسهٔ تراکنش، مبلغ و پرداخت‌کنندهٔ همان تلاش را به‌صورت پایدار ثبت می‌کند. پس از رسید موفق یا در بازیابی توسط worker، این اطلاعات با `inquireTransaction` تطبیق داده می‌شوند؛ فقط نتیجهٔ منطبق با وضعیت `paid` مسیر مالی سفارش را اجرا می‌کند. **بازیابی توسط worker برای تراکنش دارای تأیید اولیهٔ ثبت‌شده، به دریافت رویداد `successful_payment` وابسته نیست.** اگر رویداد بله نرسد یا از دست برود، worker می‌تواند همان تراکنش ثبت‌شده را مستقلاً استعلام کند؛ نبود رسید باعث موفق فرض‌کردن پرداخت نمی‌شود.

تغییر توکن ربات یا توکن کیف‌پول، **حتی برای همان ربات**، به‌دلیل وابستگی تلاش‌ها به مجموعهٔ کامل credentialها، نشست‌های پرداخت باز را برای بررسی متوقف می‌کند. نام ربات و حساب دریافت‌کننده نیز باید با تنظیمات زمان ایجاد تلاش منطبق بمانند. مهاجرت خودکار تلاش‌های قبلی به credential تازه انجام نمی‌شود؛ پیش از چرخش توکن، پرداخت‌های باز را بررسی و تعیین تکلیف کنید.

تغییر `BALEPAY_WEBHOOK_SECRET` هویت حساب دریافت‌کننده را عوض نمی‌کند، اما نشانی webhook و اثرانگشت ثبت تنظیمات را تغییر می‌دهد. بنابراین تغییر secret یا origin به انتقال هماهنگ webhook و ثبت مجدد نیاز دارد. تا زمانی که webhook قبلی به نشانی متفاوت اشاره کند، `--register` متوقف می‌شود؛ اسکریپت آن را به‌صورت خودکار حذف یا بازنویسی نمی‌کند. پیش از انتقال، وضعیت پرداخت‌های باز و مصرف‌کنندهٔ فعلی رویدادها را بررسی کنید.

برای توقف پرداخت‌های جدید، `BALEPAY_ENABLED=0` قرار دهید و سرویس‌های موجود را با تنظیمات تازه راه‌اندازی کنید. توکن‌ها و webhook را حفظ کنید تا دریافت و استعلام تراکنش‌های قبلاً متصل‌شده به پرداخت‌کننده ادامه پیدا کند. تعویض توکن، رسیدهای قبلی را خودکار به حساب جدید منتقل نمی‌کند و بررسی پرداخت‌های باز لازم است.

هنگام پیگیری مشکل فقط شناسهٔ سفارش، زمان، وضعیت عمومی و نتیجهٔ boolean ابزار راه‌اندازی را به پشتیبانی بدهید. توکن‌ها، secret، نشانی کامل webhook یا payload خام رویدادهای مالی را در تیکت عمومی کپی نکنید.
