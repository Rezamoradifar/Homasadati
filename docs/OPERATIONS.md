# عملیات پشتیبانی، مالی و نگهداری

این راهنما مربوط به migration 11 است. اجرای محلی و انتشار کد به معنی نصب روی `homanets.com` نیست. مبالغ دفتر مالی ریال هستند؛ برچسب برخی جدول‌های پنل به تومان تبدیل و نمایش می‌شود. قیمت پیشنهادی کارت فیروزه ۳۰۰٬۰۰۰٬۰۰۰ ریال و زمرد ۷۰۰٬۰۰۰٬۰۰۰ ریال است؛ این قیمت، اعتبار سفر یا قاعده پورسانت نیست.

## تیکت پشتیبانی

- عضو از «پشتیبانی و درخواست‌های من» موضوع، دسته، اولویت، متن و در صورت نیاز شناسه سفارش خودش را ثبت می‌کند. هر عضو حداکثر ۲۰ درخواست باز دارد. پیام‌ها متنی‌اند؛ پیوست فایل هنوز پشتیبانی نمی‌شود.
- نقش پشتیبانی یا نقش اختصاصی دارای `tickets:read` درخواست‌ها را می‌بیند؛ پاسخ، یادداشت داخلی و تغییر وضعیت به `tickets:write` نیاز دارد. یادداشت داخلی از API و صفحه عضو حذف می‌شود، نه اینکه صرفاً با CSS مخفی باشد.
- پاسخ عمومی پشتیبان درخواست را «در انتظار کاربر» و پاسخ عضو آن را «در انتظار پشتیبانی» می‌کند. پاسخ عمومی به درخواست بسته‌شده آن را باز می‌کند. یادداشت داخلی وضعیت را تغییر نمی‌دهد.
- تغییر وضعیت و مسئول با نسخه رکورد کنترل می‌شود تا تغییر هم‌زمان همکاران بی‌صدا بازنویسی نشود. اعلان بیرونی فقط وجود پاسخ را اعلام می‌کند؛ متن پیام خصوصی به پیامک/ایمیل فرستاده نمی‌شود.

## تأیید دو نفر برای پرداخت

پیش از ارتقا حداقل دو حساب مجاز مالی، مستقل از حساب ذی‌نفع، آماده کنید. حساب‌ها مشترک نباشند؛ هر عمل با هویت همان مدیر ثبت می‌شود.

**برداشت عضو:** مدیر اول مبلغ رزروشده را تأیید می‌کند. پس از انتقال واقعی وجه، مدیر دیگری وضعیت پرداخت‌شده و مرجع بانکی را ثبت می‌کند. صاحب برداشت، حتی مدیر اصلی، مجاز به تأیید پرداخت خودش نیست. مجوز و مسدودنبودن مدیر اول در مرحله دوم دوباره بررسی می‌شود. اگر مدیر اول دیگر مجاز نیست، درخواست را با دلیل رد و به موجودی برگردانید و فرایند تازه‌ای آغاز کنید. تکرار پرداخت با مرجع متفاوت خطا می‌دهد.

درخواست‌های تأییدشده قبل از migration 11 تأییدکننده ثبت‌شده ندارند: یک مدیر مجاز ابتدا همان وضعیت «تأییدشده» را ثبت کند؛ این کار مبلغ را دوباره کسر نمی‌کند. سپس مدیر دوم پرداخت را ثبت کند. پرداخت‌های قطعی قدیمی بازنویسی نمی‌شوند.

**پذیرنده:** ثبت‌کننده مبلغ و مرجع پرداخت بانکی انجام‌شده را پیشنهاد می‌کند؛ مبلغ برای بررسی رزرو می‌شود. مدیر دوم مستقل از ثبت‌کننده و مالک قرارداد، آن را تأیید یا رد می‌کند. دفتر تسویه فقط بعد از تأیید دوم نوشته می‌شود. مرجوعی یا کاهش مانده می‌تواند تأیید را متوقف کند؛ پس از بررسی، پیشنهاد را رد و مورد صحیح را دوباره ثبت کنید. تغییر مالک قرارداد برای دورزدن منع تأیید ذی‌نفع مؤثر نیست؛ مالک زمان ثبت نیز نگهداری می‌شود.

این ابزار **وجه بانکی انتقال نمی‌دهد**. اتصال پرداخت خودکار به قرارداد API بانک/ارائه‌دهنده، دسترسی و آزمون تطبیق واقعی نیاز دارد.

## زمان‌بندی باینری

مدیریت ← «زمان‌بندی تسویه باینری»: هنگام خرید (پیش‌فرض)، روزانه یا هفتگی؛ ساعت و روز بر اساس تهران. انتخاب روی سفارش‌های جدید snapshot می‌شود و سفارش قبلی را تغییر نمی‌دهد. نرخ و نسبت از قواعد مالی مصوب همان سفارش می‌آید؛ نرخ تازه‌ای به‌صورت خودکار ساخته نمی‌شود.

- worker هر ۳۰ ثانیه دوره‌های رسیده را بررسی می‌کند. پس از قطعی، آخرین مرز دوره را پردازش می‌کند؛ دوره‌های ازدست‌رفته پرداخت تکراری ایجاد نمی‌کنند.
- فقط سفارش پرداخت‌شده قبل از مرز دوره و حجم ایجادشده تا آن مرز قابل بررسی است. ذی‌نفعان همان جایگاه ثبت‌شده فروش هستند.
- بودجه برابر سقف پورسانت سفارش منهای اسناد غیرمرجوع ثبت‌شده است. خرید تازه برای اجرای دوره بعد لازم نیست، اما حجم انتقالی بدون بودجه واقعی وعده پرداخت نیست.
- صلاحیت فعالیت، انقضای حجم و سقف روزانه در زمان اجرای واقعی کنترل می‌شوند. بلوغ پورسانت از مهلت لغو سفارش تأمین‌کننده بودجه و سفارش‌های حجم مصرف‌شده زودتر نیست.
- حداکثر ۱۰۰ سفارش در یک نوبت worker، ۵۰ سفارش از هر زمان‌بندی و ۵۰۰ تطبیق برای هر سفارش در هر دوره پردازش می‌شود. ادامه حجم در دوره بعد بررسی می‌شود. توقف عمومی پورسانت، پردازش دوره‌ای را هم متوقف می‌کند.
- شناسه سفارش و دوره یکتا است؛ دفتر تطبیق و منابع حجم برای مرجوعی نگهداری می‌شوند. جدول پنل ۱۰۰ پردازش آخر، حتی پردازش با مبلغ صفر، را نشان می‌دهد.

این مدل از بودجه هر فروش استفاده می‌کند؛ یک استخر مالی نامحدود یا تقسیم بودجه جهانی بین همه اعضا نیست. تغییر مدل تجاری به محاسبه و قواعد جدا نیاز دارد.

## نصب یا ارتقای نسخه روی VPS

این محیط به VPS مالک متصل نیست. مسیرهای زیر برای نصب مستندشده `/opt/homay/app`، کاربر `homay`، سرویس `homay` و Node 22 هستند؛ اگر نصب شما متفاوت است ابتدا مسیر و نام سرویس را تطبیق دهید. کلید اصلی رمزگذاری موجود را عوض نکنید.

1. ابتدا نسخه پشتیبان آنلاین بگیرید، مسیر خروجی آن را نگه دارید و بازیابی آزمایشی را اجرا کنید:

```bash
cd /opt/homay/app
sudo -u homay npm run platform:backup -- /opt/homay/backups
```

با مسیر واقعی چاپ‌شده در مرحله قبل:

```bash
sudo -u homay npm run platform:restore-drill -- /opt/homay/backups/TIMESTAMP
```

2. تغییرات محلی و شاخه را با `git status` بررسی کنید. ابتدا آخرین نسخه شاخه `feature/customer-club-complete` را در Staging بسازید و سناریوی سفارش/مرجوعی/دو مدیر را با داده آزمایشی بررسی کنید. فایل‌های خصوصی و پوشه داده را وارد git نکنید.
3. برای نصب فعلی روی همین شاخه، در پنجره نگهداری وب و worker را متوقف کنید؛ `git pull --ff-only origin feature/customer-club-complete`، سپس `npm ci --no-audit --no-fund` و `npm run build` را با کاربر مالک فایل‌ها اجرا کنید. اگر شاخه محلی یا تاریخچه متفاوت است از `reset --hard` استفاده نکنید؛ ابتدا تغییرات را حفظ و تطبیق دهید. build نباید روی پوشه خروجی برنامه در حال اجرا انجام شود.
4. فقط پس از build موفق `sudo systemctl restart homay homay-worker` و بررسی `sudo systemctl status homay homay-worker` را انجام دهید. migration افزایشی در اولین دسترسی دیتابیس اجرا می‌شود. صفحه `/api/health`، ورود، محصول و عملیات مالی موجود را بررسی کنید؛ `/api/health/ready` معیار کامل‌تر عملیات است.
5. اگر ارتقا شکست خورد، سرویس را تا تشخیص علت باز نکنید. برای برگشت به نسخه قبلی، کد و دیتابیس/تصاویر همان نسخه پشتیبان و کلید اصلی را با هم برگردانید. بازیابی آزمایشی هیچ‌وقت دیتابیس زنده را تغییر نمی‌دهد.

اگر محیط اصلی از `EnvironmentFile` جدا استفاده می‌کند، همان مقادیر `DATABASE_PATH` و `PLATFORM_MASTER_KEY` باید به worker، بکاپ و پایش برسند؛ `.env.local` صرفاً یکی از روش‌های پیکربندی است.

## پشتیبان رمزگذاری‌شده خارج از سرور

اسکریپت `platform:offsite-backup` از ابزار مستقل **Restic** استفاده می‌کند؛ نصب آن از بسته رسمی سیستم‌عامل یا انتشار رسمی بر عهده مدیر سرور است. قبل از فعال‌سازی، `restic version` باید موفق شود. این ابزار جزو وابستگی npm نیست.

1. یک مخزن اختصاصی روی S3/SFTP/REST HTTPS یا backend پشتیبانی‌شده تهیه کنید؛ دسترسی نوشتن باید محدود به همان مخزن باشد. رمز رمزگذاری حداقل ۳۲ کاراکتر در فایل خصوصی قرار می‌گیرد؛ یک کپی امن جدا از VPS برای بازیابی نگه دارید.
2. پوشه تنظیمات و فایل نمونه را نصب و سپس **روی سرور** مقادیر واقعی را وارد کنید:

```bash
sudo install -d -m 750 -o root -g homay /etc/homay
sudo install -m 600 deploy/operations.env.example /etc/homay/operations.env
sudoedit /etc/homay/operations.env
```

فایل `/etc/homay/operations.env` مخصوص root است. فایل‌های ارجاع‌شده `restic-repository.private` و `restic-password.private` باید متعلق به `homay` با مجوز `0600` باشند. فایل repository یک خط حاوی مقصد واقعی دارد. کلیدهای ارائه‌دهنده را فقط در تنظیمات خصوصی نگه دارید؛ به گفتگو یا مخزن عمومی نفرستید. مقصد پیش‌فرض یا کلید آزمایشی قابل استفاده وجود ندارد.

3. مخزن جدید را فقط یک بار، با همان متغیرهای محیطی و هویت سرویس، با `restic init` ایجاد کنید. مخزن موجود را دوباره ایجاد نکنید. راهنمای رسمی [ساخت مخزن](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html) و [اجرای خودکار](https://restic.readthedocs.io/en/stable/075_scripting.html) تنظیمات هر backend را توضیح می‌دهد.
4. پس از تنظیم مقصد، رمز و دسترسی واقعی:

```bash
sudo install -d -m 700 -o homay -g homay /opt/homay/backups
sudo install -m 644 deploy/homay-offsite-backup.service deploy/homay-offsite-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start homay-offsite-backup.service
sudo systemctl status homay-offsite-backup.service
sudo systemctl enable --now homay-offsite-backup.timer
```

اجرا ابتدا بکاپ سازگار SQLite و آزمون بازیابی در کپی موقت می‌سازد، سپس آن را رمزگذاری و به مخزن می‌فرستد. تنها exit code صفر، وجود شناسه snapshot و مشاهده آن در فهرست مخزن موفق محسوب می‌شود؛ exit code 3 آپلود ناقص است. جزئیات در [راهنمای Backup رسمی Restic](https://restic.readthedocs.io/en/stable/040_backup.html) آمده است. لاگ برنامه خروجی خام ارائه‌دهنده را برای جلوگیری از افشای کلید چاپ نمی‌کند.

زمان پیش‌فرض حدود ۰۴:۰۰ به وقت سرور است. آخرین موفقیت در پنل نمایش داده می‌شود. `--local-rehearsal` تمرین با مخزن محلی است و سلامت offsite ثبت نمی‌کند. در این نسخه آزمون subprocess با قرارداد شبیه‌سازی‌شده Restic و دیتابیس/بازیابی واقعی محلی انجام شده؛ رمزگذاری و انتقال به مخزن واقعی هنوز در محیط مالک آزموده نشده است.

حذف خودکار نسخه‌های قدیمی فعال نیست. برنامه نگهداری متناسب با ظرفیت تهیه کنید؛ دستور `forget/prune` بدون بازبینی نسخه‌ها اجرا نکنید. دست‌کم ماهانه از مخزن بیرونی به یک مسیر خالی restore کنید، سپس `platform:restore-drill` را روی پوشه بازیابی‌شده اجرا کنید. آزمون پیش از آپلود جای آزمون دریافت واقعی از مقصد را نمی‌گیرد.

## پایش و هشدار

`npm run platform:monitor` سلامت دیتابیس، worker (۳ دقیقه)، بکاپ محلی و بیرونی (۳۶ ساعت)، فضای دیسک (پیش‌فرض ۵۱۲ MiB)، اعلان‌های با ۸ تلاش ناموفق و پاسخ وب محلی را بررسی می‌کند. خروجی JSON داده شخصی یا کلید ندارد؛ مشکل عملیاتی exit code 1 دارد.

در `operations.env` یک `ALERT_WEBHOOK_URL` واقعی HTTPS قرار دهید. گیرنده باید POST JSON عمومی با فیلدهای `service`, `status`, `checks`, `checkedAt` و پاسخ موفق 2xx را بپذیرد؛ این فرمت مستقیماً قالب اختصاصی Slack/Telegram نیست و ممکن است به واسط نیاز داشته باشد. دستور با `--notify` ارسال را فعال می‌کند. وضعیت یکسان تا یک ساعت تکرار نمی‌شود؛ تغییر وضعیت و بازیابی گزارش می‌شوند و شکست ارسال قابل تلاش مجدد است.

```bash
sudo install -m 644 deploy/homay-monitor.service deploy/homay-monitor.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start homay-monitor.service
sudo systemctl enable --now homay-monitor.timer
sudo systemctl list-timers homay-monitor.timer homay-offsite-backup.timer
```

پایش هر پنج دقیقه اجرا می‌شود. شکست ارسال یا نبود مقصد، هشدار تحویل‌شده محسوب نمی‌شود. برای تشخیص خاموشی کامل VPS، یک ناظر **بیرون از VPS** باید `/api/health/ready` را بررسی کند. توکن تصادفی حداقل ۳۲ کاراکتر را به نام `MONITOR_TOKEN` در محیط خصوصی وب و ناظر قرار دهید؛ درخواست با `Authorization: Bearer TOKEN` فرستاده شود. پاسخ بدون توکن 401، سالم 200 و نیازمند بررسی 503 است. توکن را در query URL قرار ندهید. endpoint توکن‌دار شامل وضعیت بکاپ/worker هم هست؛ `/api/health` فقط زنده‌بودن وب است.

## موارد لازم از مالک برای فعال‌سازی واقعی

- تأیید نرخ‌ها، سقف‌ها، نسبت، شرایط فعالیت، لغو و زمان‌بندی باینری در پنل؛ دو مسئول مالی مستقل.
- اطلاعات واقعی محصول، ظرفیت، قرارداد پذیرنده، حساب مقصد و محتوای فارسی/انگلیسی/عربی.
- تنظیم خصوصی درگاه، پیامک، ایمیل، کپچا و گوگل مطابق `AUTHENTICATION.md`؛ آزمون پرداخت و تحویل واقعی.
- مقصد و دسترسی Backup، رمز مستقل Restic، گیرنده هشدار و ناظر بیرونی.
- برای انتقال خودکار بانک یا صدور خودکار سفر/اشتراک خارجی: انتخاب ارائه‌دهنده و مستندات/دسترسی API واقعی.

کلید خصوصی، رمز حساب، OTP و داده کامل کارت بانکی را در پیام یا GitHub ارسال نکنید؛ آن‌ها فقط در تنظیمات خصوصی سرویس قرار می‌گیرند.
